# 03 · 组件设计（Component Design）

## 一句话定位
挑几个最关键的函数/类，讲清楚"它们怎么协作把一次研究跑完"。

## 关键协作链路 1：受控工具（大脑的牢笼）
- 注册：`run_tools.ts` 的 `TOOL_DEFS` 列出 5 个工具——`listRunFiles`(列)、`readRunFile`(读)、`runCalculation`(算)、`writeStageOutput`(写产物)、`writeReport`(写报告)。
- 入口：`callRunTool(ctx, name, rawArgs)` —— **先 `z.object(def.inputShape).safeParse` 验参，再执行**（`run_tools.ts:301`），谁也绕不开校验。
- 暴露给大脑：`finance/run_tools_mcp.ts` 的 `buildRunToolsServer` 把这些打包成 MCP server。大脑（没有 Shell/文件全权）只能调这 5 个。
- 直连引擎：`engines/direct_stage_agent.ts` 用 `runToolsAsFunctionSpecs()` 把同一份 `inputShape` 转成 function-calling 工具表交给大脑。

## 关键协作链路 2：确定性计算
- 大脑通过受控工具 `runCalculation` 触发；底层落到 `calc/cli.py` 的 `run` → 在 `FUNCTIONS` 表里按名取纯函数（`chip_distribution`/`ttm_sum`/`ratio`…）。
- 安全校验：`calc/contracts.py` 的 `validate_contract` 只核对"参数类型 + JSON 结构"，**不执行公式本体**，避免把任意代码当计算跑。

## 关键协作链路 3：合并与冲突
- `merge.ts` 的 `loadFetch` 扫 `fetch/`；`mergeEvidence` 按 id 去重（同 id 不同值 → `idConflicts`）；`detectSourceConflicts` 找同源分歧 → `sourceConflicts`。
- `writeMergedArtifacts(cfg)` 一次性落盘 `evidence.json`/`calculations.json`/`conflicts.json`。

## 关键协作链路 4：大脑解析
- `runtime_provider.ts`：`resolveRuntimeProvider` 区分 `local-agent`（Claude/Codex/CodeBuddy，读用户自己登录）与 `api`（模型API，key 进它自己的 `env_key`）。
- `researchRuntimeEnv` 产出一组**安全环境变量**给子进程——key 绝不落盘、绝不改写 `VRA_*`（`service.ts:177`）。

## 数据流一图
```
大脑(5工具) → 写 stages/<s>.json + fetch/ + calcs/ + report
                │
                ▼
            merge.ts → evidence.json / calculations.json / conflicts.json
                │
                ▼
         validator.ts 收工检查 → 下一阶段 / 报告
```

## 小结
组件设计的核心是"**所有写操作都过受控工具 + 所有校验都过 schema**"——这是把纪律硬编码进代码的范例。
