# 02 · 架构师视角：值对象为什么"冻结不可变"（Value Objects）

> 配套 `01-值对象.md`。

## 作者为什么这样设计
`FetchEnvelope`（取数账本）、`EvidenceItem`（证据）、`CalcRecord`（计算记录）被设计成**一旦产生就不可变的事实快照**。为什么不能改？因为研究的"证据链"是审计核心——如果一条证据事后被改，就再也追不回"当时到底依据了什么"。证据：`merge.ts` 里 `mergeEvidence` 按 id 去重，同 id 不同值直接记为冲突（而不是覆盖）；`schemas.ts` 的 `fetchEnvelopeSchema`/`calcRecordSchema` 只描述"它长什么样"，不提供"改它"的接口。

**意图**：把"已经发生的取数/计算"当成**不可篡改的事实**，既支撑审计，也让合并逻辑只需"追加+去重"，不必处理原地修改。

## 借鉴了什么
- **DDD 值对象**：无标识、靠内容判等、不可变。
- **函数式不可变 (Immutability)**：事实即值，数据不可变。

## 用了什么设计模式
| 模式 | 落点 | 作用 |
|------|------|------|
| **值对象 (Value Object)** | FetchEnvelope/EvidenceItem/CalcRecord 通过 schema 定义，靠内容判等 | 无主键、可去重 |
| **不可变事实 (Immutable Fact)** | 合并只"追加/去重"，不原地改 | 支撑审计与重放 |
| **规约去重** | `mergeEvidence` 的 id 冲突规则 | 内容相等即同一对象 |

## 小白一句话
值对象不是"可编辑的档案"，而是"拍下的照片"——取数那一刻定格，之后只能引用它、不能改它。想改？重新取一次，生成一张新照片，旧照片原样留着当证据。
