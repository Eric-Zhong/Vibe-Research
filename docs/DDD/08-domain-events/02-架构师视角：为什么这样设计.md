# 02 · 架构师视角：领域事件为什么是"隐式文件事件"（Domain Events）

> 配套 `01-领域事件.md`。

## 作者为什么这样设计
通常领域事件要靠消息总线（Kafka/RabbitMQ 之类）发布订阅。本项目**没有引入任何消息中间件**，而是用"**上一阶段写文件 = 发布事件，下一阶段读文件 = 消费事件**"来表达。为什么这么"土"？因为：
1. 研究流程是**线性、可重放**的，不需要实时广播；
2. 文件本身就是**持久化的事件日志**，崩溃后重跑能从断点续上；
3. 省掉一个外部依赖，本地工具更稳更简单。

证据：阶段产物经 `writeStageOutput` 落盘后，编排器才推进下一阶段（`orchestrate.ts`）；回测/辩论完成会"自动写入本地记录"（`AGENTS.md` §6.1）；`conflicts.json` 由 merge 阶段产出、risk/report 阶段消费。

## 借鉴了什么
- **DDD 领域事件**：跨聚合/上下文传递"已发生的事实"。
- **事件溯源 / 发件箱模式 (Outbox) 轻量版**：写文件既存状态又发事件，二者原子（同一落盘动作）。
- **最终一致性**：下游阶段读到上游文件即为"事件被消费"。

## 用了什么设计模式
| 模式 | 落点 | 作用 |
|------|------|------|
| **基于文件的事件 (File-as-Event)** | 阶段写文件 / 下一阶段读文件 | 免消息总线 |
| **发件箱模式 (Outbox-lite)** | 状态写入与事件发布同一动作 | 不丢事件 |
| **自动归档** | 回测/辩论完成写本地记录 | 事件触发持久化 |

## 小白一句话
在这里，"保存一个文件"就等于"广播一条消息"。下一阶段只要看到这个文件，就知道"上一步搞定了，轮到我了"。不需要额外的消息队列——文件系统就是最朴素的事件总线，还顺带能重放。
