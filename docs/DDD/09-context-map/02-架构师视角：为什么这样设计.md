# 02 · 架构师视角：上下文映射为什么需要"防腐层"（Context Map）

> 配套 `01-上下文映射.md`。

## 作者为什么这样设计
9 个上下文里，最危险的关系是"**产品 ↔ 外部大脑（AI）**"。大脑是**不受信任、且会执行任意文本**的外部实体，如果让它直接碰文件系统或 Shell，后果不可控。作者用一道**防腐层 (ACL)** 把大脑关进只有 5 个受控工具的小笼子。证据：
- `finance/run_tools_mcp.ts` 的 `buildRunToolsServer` 把内部能力包成 MCP 工具交给大脑；
- 大脑**没有** Shell/网络/任意文件读写（`AGENTS.md` §1）；
- `runtime_provider.ts` 的 `researchRuntimeEnv` 强制：模板 `env_key` 不能是 `VRA_*`、不能借模板改写基础环境，key 只进它自己的变量（`service.ts:177`）。

此外还有"共享内核"：桌面与编排器共用 `data_root.ts` 解析数据根（`desktop/vite-token.ts` 的 `apiTokenPath`），但只共享配置、不共享业务。

## 借鉴了什么
- **DDD 上下文映射**：显式画出上下文关系。
- **防腐层 (Anti-Corruption Layer, ACL)**：在"聪明但不受信的大脑"与"受保护的产品核心"之间放一个翻译+门禁层。
- **六边形架构 (Ports & Adapters)**：MCP 工具就是朝大脑开的"端口"；`runToolsAsFunctionSpecs()` 还能把同一套工具适配成"函数调用"形态喂给不同引擎。

## 用了什么设计模式
| 模式 | 落点 | 作用 |
|------|------|------|
| **防腐层 (ACL)** | `buildRunToolsServer` 收窄能力为 5 工具 | 大脑看不到文件系统全貌 |
| **适配器 (Adapter)** | `runToolsAsFunctionSpecs()` 转 function-calling | 同一能力适配多种引擎 |
| **共享内核 (Shared Kernel)** | `data_root.ts` 被桌面+编排器共用 | 仅共享配置，不共享逻辑 |
| **客户-供应商** | 桌面 `api.ts` 遵奉编排器 API | 前后端契约一致 |

## 小白一句话
防腐层就是"翻译官 + 保安"：大脑很聪明，但不能让它乱跑。产品通过 MCP 只给它 5 个工具，就像给外聘专家发了一张"只能进指定房间的门禁卡"——能干正事，碰不到保险柜。
