# 06 · 领域服务（Domain Services）

## 一句话定位
有些行为"不属于任何一个实体"——它协调多个对象完成一件事，这种无家可归的行为就是领域服务。

## 小白怎么理解
"把取数账本合并成证据"这种活，不属于任何一条证据，它横跨很多条记录——这种"跨对象的操作"就是领域服务。

## 本项目的领域服务
| 服务 | 职责 | 代码落点 |
|------|------|----------|
| 合并服务 Merge | 把 fetch 去重合并成 evidence/calcs，并检测冲突 | `merge.ts` 的 `mergeEvidence`、`detectSourceConflicts`、`writeMergedArtifacts` |
| 校验服务 Validator | 校验阶段产物是否齐、是否合规（收工闸门） | `validator.ts` 的 `validateStage`、`StageOutput` |
| 受控工具执行服务 RunTools | 统一入口执行 5 个受控工具，先验参再执行 | `run_tools.ts` 的 `callRunTool`（`z.object(def.inputShape).safeParse` 后执行，谁也别想绕开校验） |
| 大脑解析服务 RuntimeProvider | 决定"谁来想"：本地订阅 Agent 还是模型 API，产出安全的环境变量 | `runtime_provider.ts` 的 `resolveRuntimeProvider`、`researchRuntimeEnv` |
| 确定性计算服务 Calc | 跑纯函数计算并校验契约（签名 + JSON 类型，不真跑公式） | `calc/contracts.py` 的 `validate_contract`、`cli.py` 的 `run` |

## 为什么它们不是聚合根的方法
- 合并、校验、受控工具执行，都**跨多个 Stage/Record**，只挂在某个实体头上说不通。
- 它们被编排器在"每阶段开始前/结束时"统一调用，是**流程级**行为而非对象级。

## 小结
领域服务是 DDD 里的"跨部门流程"；本项目的 Merge / Validator / RunTools 正是把"研究流程的纪律"集中实现的地方。
