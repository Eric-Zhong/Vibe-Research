# 02 · 架构师视角：领域服务为什么是"跨聚合的流程"（Domain Services）

> 配套 `01-领域服务.md`。

## 作者为什么这样设计
合并（Merge）、校验（Validator）、受控工具执行（RunTools）、大脑解析（RuntimeProvider）这些行为，**不属于任何单个实体**——它们横跨多个 Stage/Record 协调。作者把它们抽成领域服务，集中在编排器"每阶段前/后"统一调用，把"研究流程的纪律"收口到少数几处。证据：
- `merge.ts` 的 `mergeEvidence`/`detectSourceConflicts`/`writeMergedArtifacts`——合并与冲突服务。
- `validator.ts` 的 `validateStage`/`StageOutput`——收工闸门。
- `run_tools.ts` 的 `callRunTool`——**先 `z.object(def.inputShape).safeParse` 验参，再执行**（`run_tools.ts:301`），谁也绕不开校验。
- `runtime_provider.ts` 的 `resolveRuntimeProvider`/`researchRuntimeEnv`——决定"谁来想"并产出安全环境变量。

## 借鉴了什么
- **DDD 领域服务**：无家可归的跨对象行为集中成服务。
- **规格模式 (Specification)**：`schemas.ts` 的 `validateWith(name, schema, data)` 把"某物是否合规"表达成一个个可组合的真假判定（每个阶段的 `stageValidators` 也由插件提供）。
- **命令模式 (Command) + 注册表**：`run_tools.ts` 的 `TOOL_DEFS` 把 5 个受控工具登记为"带 inputShape + run 的命令"，`callRunTool` 按名分发。
- **策略模式 (Strategy)**：`resolveRuntimeProvider` 在"本地订阅 Agent(claude/codex/codebuddy)"与"模型 API"之间按配置选一种。

## 用了什么设计模式（汇总）
| 模式 | 落点 |
|------|------|
| 领域服务 (Domain Service) | Merge / Validator / RunTools / RuntimeProvider |
| 规格模式 (Specification) | `validateWith`、各 `validateXxx`、`stageValidators` |
| 命令模式 (Command) | `TOOL_DEFS` + `callRunTool` 分发 |
| 策略模式 (Strategy) | `resolveRuntimeProvider` 选大脑类型 |

## 小白一句话
领域服务就是"跨部门流程"：实体自己管不了"把一堆碎片合并成证据"这种跨对象的大动作，于是交给了服务。而且这里每个服务都带**强制校验**——工具调用先验参、阶段产物先过规约，把纪律写进了代码。
