# 04 · 聚合根、实体与一致性边界（Aggregates）

## 一句话定位
有些数据必须"整组一起改、一起对"，这组就叫一个聚合。聚合根是对外唯一的大门。

## 小白怎么理解
把"一次研究运行（Run）"看作一个聚合根：它内部的 Manifest、各阶段产物、证据、计算记录，必须**整体一致**才算数。
你不能直接去改某条证据而不经过合并逻辑——得走聚合根规定的入口。

## 本项目的聚合
### 聚合根：Run（研究运行）
- 入口：`merge.ts` 的 `writeMergedArtifacts(cfg)` —— 统一负责把 fetch 合并成 evidence/calcs/conflicts 并落盘。
- 内部实体：`StageRecord`（`merge.ts:154`，记录每个阶段的产物状态）、`EvidenceItem`、`CalcRecord`、`SourceConflict`。
- 一致性保证：
  - 同 id 不同值 → 记为 **id 冲突**（`idConflicts`）；
  - 同源不同结论 → 记为 **source 冲突**（`sourceConflicts`）。
  - 这些都写进 `conflicts.json`，由后续 risk/report 阶段与 validator 核对。

### 聚合根：Backtest（回测）
- 入口：桌面侧 `backtestView.ts` 的 `BacktestView` 结构，由回测工具结果一次性构造（`matrix`/`errorOf` 解析）。
- 内部值：`Cell`、`ChartSeries`、`MonthlyTable`——只作为展示聚合的组成部分，不独立写库。

## 为什么不能绕过
大脑想收工时，产品先做**收工检查**：产物缺失或校验不过，就把问题清单交回去重做（`validator.ts` 的 `validateStage`）。这就是聚合根的"一致性闸门"。

## 小结
"Run 聚合"把"散落各处的文件"收敛成一个可被整体校验的业务对象，是本系统可审计性的核心。
