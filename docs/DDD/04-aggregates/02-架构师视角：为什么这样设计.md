# 02 · 架构师视角：聚合根为什么是"唯一写入口"（Aggregates）

> 配套 `01-聚合与一致性边界.md`。

## 作者为什么这样设计
一次研究里，取数、计算、各阶段会**并发/先后产出大量碎片**（fetch、calc、stage 产物）。如果谁都能直接写 `evidence.json`/`conflicts.json`，就会出现"半成品"或"互相矛盾的结论"混进报告。作者把"研究运行（Run）"定为聚合根，并规定**只有一个合并入口**能写出最终证据与冲突。证据：`merge.ts` 的 `writeMergedArtifacts(cfg)` 统一负责把 fetch 合并成 evidence/calcs/conflicts 并落盘；`mergeEvidence` 按 id 去重，冲突（同 id 不同值 / 同源分歧）集中记录到 `conflicts.json`。

**意图**：用"单点写入"保证聚合内部的**一致性不变量**——进报告之前，所有碎片必须经过这一道合并闸门。

## 借鉴了什么
- **DDD 聚合根 (Aggregate Root)**：聚合根是对外唯一的大门，内部实体一致性由它担保。
- **事务一致性边界**：把"哪些写必须一起对"圈成一个边界。

## 用了什么设计模式
| 模式 | 落点 | 作用 |
|------|------|------|
| **聚合根 + 不变量** | `writeMergedArtifacts` 是唯一写 evidence/conflicts 的点 | 保证证据集自洽 |
| **工厂 (Factory)** | `RunConfig` 携带 runDir，聚合操作以它为准 | 从配置构建聚合操作上下文 |
| **规约判定** | `detectSourceConflicts` 判定"同源矛盾" | 把业务规则收口 |

## 小白一句话
聚合根像个**守门员**：任何研究碎片想进"证据库"，都必须先过 `writeMergedArtifacts` 这道门；门会检查"有没有重复 id、有没有自相矛盾"，不放行的绝不进报告。
