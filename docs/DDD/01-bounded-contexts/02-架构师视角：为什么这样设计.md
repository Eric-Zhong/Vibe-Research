# 02 · 架构师视角：限界上下文为什么这样切（Bounded Contexts）

> 配套 `01-限界上下文划分.md`。这里讲**作者为什么这么切、借鉴了谁、用了什么模式**。

## 作者为什么这样设计
这个项目表面是"炒股研究工具"，但作者**没有把它写成一套写死金融逻辑的程序**，而是把"研究编排"抽成了与行业无关的 Core，金融只是插进来的一个领域插件。证据：
- `orchestrator/src/plugin.ts` 定义了 `Plugin` 接口（`plugin.ts:135`），金融逻辑全在 `orchestrator/src/finance/plugin.ts`（`FINANCE_PLUGIN`）。
- 全项目通过一个**唯一入口** `currentPlugin()`（`plugin.ts:1595`，被 115 处调用）拿到当前领域插件——没有任何业务代码直接 `import finance`。
- `orchestrator/test/core_purity.test.ts` 是一条**架构护栏测试**：Core 里出现任何行业词（股票/财报等）就报错。这是把"限界上下文边界"用测试**硬编码**成了不可逾越的墙。

**意图**：让同一套编排引擎能服务多个"垂直领域"（finance 只是第一个），未来换领域不用重写引擎。

## 借鉴了什么
- **DDD 限界上下文**：把"通用研究流程"与"具体行业知识"分成两个互相不污染的上下文。
- **六边形架构（Ports & Adapters）/ 端口与适配器**：Core 是"应用核心"，`Plugin` 接口就是朝外的**端口**；`finance/plugin.ts` 是插进来的**适配器**。核心不依赖具体领域，领域反过来依赖核心定义的端口（依赖倒置）。
- **插件化（Plugin Architecture）**：运行时通过注册表加载领域插件。

## 用了什么设计模式
| 模式 | 落点 | 作用 |
|------|------|------|
| **插件模式 (Plugin)** | `Plugin` 接口 + `currentPlugin()` | 领域逻辑可插拔 |
| **注册表模式 (Registry)** | `registry.ts` 的 `REGISTRY_REL`/`loadRegistry`/`Registry` | 集中登记与加载插件/阶段计划 |
| **依赖倒置 (DIP)** | Core 只依赖 `Plugin` 抽象，`core_purity.test.ts` 强制 | 核心与具体领域解耦 |
| **不可变配置** | `plugin.ts` 的 `deepFrozen` | 插件契约一旦加载就冻结，防运行时篡改 |

## 小白一句话
把 Core 想成"游戏引擎"，金融想成"一个 MOD/DLC"——引擎不认识游戏内容，靠 MOD 提供的接口表才知道这局该怎么玩。`core_purity.test.ts` 就是"引擎代码里不许出现游戏专有名词"的警察。
