# 02 · 架构师视角：领域模型为什么是"一堆 JSON 文件"（Domain Model）

> 配套 `01-领域模型.md`。

## 作者为什么这样设计
通常 OOP 的领域模型是内存里的类对象；但这里，**一次研究的领域模型被表达成 `runDir` 下的一组 JSON 契约文件**（manifest、stages、fetch、calcs、evidence、conflicts、report）。为什么不用类？三个硬约束逼出来的：
1. **大脑在进程外**：真正"想"的 AI 不在同一个程序里，它和编排器只通过文件/工具通信，内存对象传不过去。
2. **必须可审计、可重放**：研究结论要能事后核查"当时到底取了什么、算了什么"。
3. **必须确定性**：同样的输入要能复现同样的产物。

证据：`schemas.ts` 里 `manifestSchema()`、`stageOutputSchema(stage)`、`fetchEnvelopeSchema()` 等是模型的"形状定义"；`merge.ts` 的 `loadFetch`/`loadCalcs` 从文件重建模型状态。

## 借鉴了什么
- **DDD 领域模型**：识别核心概念（Run/Stage/Manifest/Evidence/Calc/Report）。
- **事件溯源 (Event Sourcing) 的变体**：状态不是"当前快照"，而是"一系列被写下的产物文件"的累积——读的时候再合并。
- **契约优先 (Schema/Contract First)**：先定 JSON Schema，再写代码，模型以契约为准。

## 用了什么设计模式
| 模式 | 落点 | 作用 |
|------|------|------|
| **规格模式 (Specification)** | `schemas.ts` 的 `validateWith(name, schema, data)` 及各 `validateXxx` | 每个契约是一个可组合的真假判定 |
| **值基模型 (Value-based Model)** | 模型实体皆为 JSON 值，无可变对象 | 天然可序列化、可重放 |
| **工厂 (Factory)** | `merge.ts`/`registry.ts` 从磁盘构建 Run/StagePlan | 从文件"造"出领域对象 |

## 小白一句话
别的系统的"领域对象"住在内存里；这里的领域对象**住在文件夹里**——一个 `runDir` 就是一个研究对象的全部状态。这让"研究过程"变成了可以回放、可以审计的"文件流水账"。
