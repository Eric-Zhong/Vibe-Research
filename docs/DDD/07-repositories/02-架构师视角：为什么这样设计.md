# 02 · 架构师视角：仓储为什么是"文件系统"（Repositories）

> 配套 `01-仓储与磁盘契约.md`。

## 作者为什么这样设计
别的项目用数据库当仓库；本项目的"仓库"是 `runDir` 下的 JSON 文件。为什么不用数据库？三个现实理由：
1. **零运维**：用户本地跑，不希望装 Postgres/SQLite 服务；Node 原生读写文件即可。
2. **可移植/隐私清晰**：所有数据在 `.local/`（`merge.ts` 的 runDir 根），一把 `gitignore` 忽略，绝不误提交（`AGENTS.md` §6.4）。
3. **天然可审计**：JSON 人能读、能 diff、能重放，契合"研究过程可核查"。

证据：`merge.ts` 的 `loadFetch`（扫 `fetch/`）、`loadCalcs`（扫 `calcs/`）、`writeMergedArtifacts`（落盘 `evidence.json`/`calculations.json`/`conflicts.json`）；`run_tools.ts` 的 `writeStageOutput` 写 `stages/<stage>.json`。

## 借鉴了什么
- **DDD 仓储 (Repository)**：隔离"领域"与"存储"，领域代码只认接口，不认底层是文件还是数据库。
- **事件溯源 (Event Sourcing) 的轻量版**：每个产物文件像一条 append-only 的事件记录。
- **CQRS 的雏形**：写操作（各阶段写碎片）与读操作（merge 读碎片、validator 读产物）分离。

## 用了什么设计模式
| 模式 | 落点 | 作用 |
|------|------|------|
| **仓储抽象** | `loadFetch`/`loadCalcs`/`writeMergedArtifacts` 等纯函数 | 领域只调"读写 JSON"，不碰 IO 细节 |
| **按契约落盘** | 所有写都先过 `validateXxx` schema | 仓库里只放合规数据 |
| **本地优先存储** | `.local/` + gitignore | 隐私与可移植 |

## 小白一句话
这里的"数据库"就是**文件夹 + JSON**。仓储就是一组"按路径读写 JSON 的纯函数"，没有 ORM、没有数据库连接——好处是：你用记事本都能打开看研究到底干了啥。
